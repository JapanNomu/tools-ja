# ソフトウェア開発の教訓

## テスト設計の原則

単体テストの期待値はIF仕様書（インターフェース仕様書）から導出する。実装コードを読んで期待値を決めることは禁止。テストが実装に引きずられると、バグを検出できないテストになる。

## V字モデルとテスト工程の対応

要件定義とシステムテストが対応する。基本設計と外部結合テストが対応する。詳細設計と内部結合テストが対応する。実装と単体テストが対応する。テストの期待値は必ず対応する設計書から導出する。

## テスト環境と本番環境の統一

テスト環境と本番環境でポート・プロトコル・設定が異なると、テストがPASSEDでも本番でエラーが発生する。特にHTTP/HTTPS混在・ポート番号の不一致は結合テストの偽PASSEDを引き起こす。

## 設計と手順の責務分離

設計書には「何をどう構成するか」を記載する。手順書には「どうセットアップするか」を記載する。両者を同一ドキュメントに入れると、設計の意図が手順の記述に埋もれて伝わらなくなる。

## 整合性チェックの順序

チェック中に問題を発見しても即座に対処しない。全量チェックが完了してから未対処リストに転記し、リスト順に1件ずつ対処する。発見即対処は見落としと作業混乱の原因になる。

## ドキュメントの格納場所

成果物の格納場所は工程・役割によって決まる。工程内のチェック記録はチェックフォルダへ。工程横断のレビュー結果はレビューフォルダへ。不備発見後の再調査は品質横展開調査フォルダへ。格納場所を間違えると後から探せなくなる。
